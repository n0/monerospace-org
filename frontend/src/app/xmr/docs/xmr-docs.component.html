FAQ

What is xmr-space?

A block & mempool explorer for Monero, forked from mempool.space. It surfaces what the Monero chain alone proves and never claims to know more than that.

What is a mempool?

The set of transactions a node knows about that haven't been confirmed in a block yet. Each Monero node maintains its own; ours is whatever monerod's get_transaction_pool returns at poll time.

Why are tx amounts shown as hidden?

Because they are hidden. Monero uses RingCT (Ring Confidential Transactions); the on-chain value of every tx output is a Pedersen commitment that only the recipient (with their view key) and the sender (with the per-tx secret key or a generated tx_proof) can decrypt. xmr-space surfaces only what the chain proves to everyone.

What's the ring size?

Sixteen, since the August 2022 hard fork. Every input is signed against a ring of 16 outputs (1 real + 15 decoys) chosen from the chain's history. Older txs may have ring size 11, 7, 5, or 3. xmr-space flags inconsistent ring sizes within a tx as a privacy red flag.

How does the four-tier fee model work?

monerod's get_fee_estimate returns four per-byte rates: slow / normal / fast / fastest. Wallets multiply by the tx weight to get the total fee. The mempool wall projects one next-block candidate from the pending txs; extra projected blocks appear only when the pool is larger than one block.

How are mining pools identified?

The /graphs/mining/pools page uses public miner-tx extra markers only. P2Pool can be identified from merge-mining tags, clear-text pool tags are matched when miners publish them, and every unattributed block stays in the Unknown bucket.

Why is there no address page?

Because Monero addresses can't be tracked from chain data alone. Outputs to an address are encrypted; only someone with the recipient's wallet/view key tooling can scan the chain for them. xmr-space does not build address histories from public chain data.

Can I verify a payment?

Yes, on /tx/:hash. Public tx_proof checks can use the backend wallet-RPC verifier. Private view-key receive scans and tx_secret_key checks run in the browser with monero-ts; the secrets are not sent to the backend or stored by xmr-space. Subaddress receive scanning from only a subaddress plus private view key is explicitly unsupported, so use tx_secret_key for subaddress payment checks.

Why no payment channels or fee-bump tools?

Those upstream wallet and fee-market workflows do not apply to Monero. Monero transactions are not mempool-replaceable in the same way, and this explorer does not offer privileged transaction-priority services.

What daemon do you talk to?

By default https://xmr-node.cakewallet.com:18081 — Cake Wallet's public node. Operators can point at any monerod via the MONEROD_RPC_URL environment variable.

How current is the data?

The backend polls the daemon every 3 seconds. New blocks and mempool deltas are pushed over WebSocket within ~5s of the daemon publishing them. Mempool stats are sampled at 1-minute intervals and persisted locally so chart history survives backend restarts.

WebSocket

ws://<host>/api/v1/ws — speaks the upstream mempool/mempool protocol so existing clients work. Send {"action":"init"} to get a snapshot, then receive pushes:

  • blocks on connect — recent block headers (oldest-first; client reverses)
  • block on every new tip
  • mempool-blocks on every mempool change
  • mempoolInfo, fees, bytesPerSecond, transactions
  • projected-block-transactions when subscribed via {"track-mempool-block": 0}

Server-Sent Events

/api/v1/events — text/event-stream. Easier to consume than WebSocket if you only need read-only updates.

  • event: snapshot on connect — current info + mempool hashes
  • event: block on every new tip — full BlockHeader
  • event: mempool-delta — {added: [hashes], removed: [hashes]}

25-second comment heartbeats keep connections alive across proxy idle timeouts.

Privacy & limitations

  • Participant proofs: private view keys and tx_secret_key material stay browser-local in the active tx page and are cleared on transaction reset. tx_proof verification can cross the wire because tx_proof signatures are non-secret by design, but it requires a configured monero-wallet-rpc backend.
  • Public daemon bridge: browser-local verification talks to same-origin /api/v1/monerod routes. Those routes allow only public monerod methods and reject secret-shaped JSON fields before proxying.
  • Fiat conversion: current and historical XMR prices are fetched server-side and stored in the local price-history index used by /graphs/price and the mining fee/reward graph fiat series.
  • Mining-pool fingerprinting: best-effort. P2Pool is detected from the public merge-mining tag in coinbase extra; clear-text centralized pool tags are matched when miners publish them, otherwise the block stays unknown.
  • Ring members: xmr-space resolves public ring-member output indices to block heights via /get_outs. This shows decoy age distribution only; it does not reveal which member was actually spent.
  • This explorer cannot tell you if you sent or received a tx unless you supply the keys. That's the whole point of Monero.
